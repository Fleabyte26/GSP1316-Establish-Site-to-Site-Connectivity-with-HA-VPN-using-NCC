# GSP1316 - Establish Site to Site Connectivity with HA-VPN using NCC

The lab does this by clicking in the console. This tutorial does the same thing from Cloud Shell, so you can see exactly what a hub and a spoke are made of.

## Known lab traps/bugs (read first)

1. Region changes per lab instance, and each spoke must be created in the region where its two tunnels live. Setup detects the tunnels and their region for each office; nothing to edit.
2. The spoke names are fixed by the lab: office-1-spoke and office-2-spoke. The hub name is your choice (this tutorial uses ncc-hub).
3. There are tunnels on both sides of each VPN (the routing-vpc side and the simulated office side). The spokes need the routing-vpc side only. Setup picks those; check that it found exactly two per office.
4. After the spokes are created, routes take 1-2 minutes to spread. A ping that fails right away usually works a minute later.
5. Do not run Task 4 (delete) until "Create Hub and Spokes" is green. Delete removes what the checker looks for.
6. The checker lags: wait 30-60 seconds and click again.

## Setup

Block 1 - facts about the two office VMs:

```bash
gcloud config get-value project > ~/project
gcloud services enable networkconnectivity.googleapis.com
gcloud compute instances list --filter="name=onprem-office1-vm" --format="value(zone.basename())" > ~/zone1
gcloud compute instances list --filter="name=onprem-office2-vm" --format="value(zone.basename())" > ~/zone2
gcloud compute instances list --filter="name=onprem-office1-vm" --format="value(networkInterfaces[0].networkIP)" > ~/ip1
gcloud compute instances list --filter="name=onprem-office2-vm" --format="value(networkInterfaces[0].networkIP)" > ~/ip2
gcloud compute instances list --filter="name=onprem-office1-vm" --format="value(networkInterfaces[0].network.basename())" > ~/net1
gcloud compute instances list --filter="name=onprem-office2-vm" --format="value(networkInterfaces[0].network.basename())" > ~/net2
head ~/zone1 ~/zone2 ~/ip1 ~/ip2 ~/net1 ~/net2
```

You should see a zone, an internal IP and a network name for each office. None may be empty.

Block 2 - find each office's VPN gateway, then the two routing-vpc tunnels that point at it:

```bash
gcloud compute vpn-gateways list --filter="network~/`cat ~/net1`" --format="value(name)" | head -1 > ~/gw1
gcloud compute vpn-gateways list --filter="network~/`cat ~/net2`" --format="value(name)" | head -1 > ~/gw2
gcloud compute vpn-tunnels list --filter="peerGcpGateway~/`cat ~/gw1`" --format="value(selfLink)" | paste -sd, - > ~/tun1
gcloud compute vpn-tunnels list --filter="peerGcpGateway~/`cat ~/gw2`" --format="value(selfLink)" | paste -sd, - > ~/tun2
gcloud compute vpn-tunnels list --filter="peerGcpGateway~/`cat ~/gw1`" --format="value(region.basename())" | head -1 > ~/reg1
gcloud compute vpn-tunnels list --filter="peerGcpGateway~/`cat ~/gw2`" --format="value(region.basename())" | head -1 > ~/reg2
head ~/gw1 ~/gw2 ~/reg1 ~/reg2
tr ',' '\n' < ~/tun1 | grep -c vpnTunnels
tr ',' '\n' < ~/tun2 | grep -c vpnTunnels
gcloud compute vpn-tunnels list --format="table(name,region.basename(),vpnGateway.basename(),peerGcpGateway.basename())"
```

You should see a gateway name and a region for each office, then 2 and 2 (two tunnels per office), then a table of all tunnels. If a count is not 2, stop and compare with the table: the tunnels you want are the ones whose gateway column belongs to routing-vpc.

## Task 1. Create the hub

A hub is just a named meeting point. It carries no traffic until spokes are attached.

```bash
gcloud network-connectivity hubs create ncc-hub --description="Site to site hub"
gcloud network-connectivity hubs list --format="table(name,state)"
```

You should see ncc-hub with state ACTIVE.

## Task 2. Create the two spokes

Each spoke wraps the two HA VPN tunnels that reach one office. The data-transfer flag is what lets office 1 reach office 2 through Google's network.

```bash
gcloud network-connectivity spokes linked-vpn-tunnels create office-1-spoke --hub=ncc-hub --region=`cat ~/reg1` --vpn-tunnels=`cat ~/tun1` --site-to-site-data-transfer
gcloud network-connectivity spokes linked-vpn-tunnels create office-2-spoke --hub=ncc-hub --region=`cat ~/reg2` --vpn-tunnels=`cat ~/tun2` --site-to-site-data-transfer
gcloud network-connectivity spokes list --region=- --format="table(name,hub.basename(),state)"
```

You should see office-1-spoke and office-2-spoke, both on ncc-hub, state ACTIVE.

Check my progress: Create Hub and Spokes.

## Task 3. Verify with ping (not scored)

Wait about a minute after the spokes are ACTIVE, then:

```bash
gcloud compute ssh onprem-office1-vm --zone=`cat ~/zone1` --quiet --command="ping -c 5 `cat ~/ip2`"
gcloud compute ssh onprem-office2-vm --zone=`cat ~/zone2` --quiet --command="ping -c 5 `cat ~/ip1`"
```

You should see 5 packets transmitted, 5 received, twice. If you get 100% packet loss, wait a minute and run it again. If the ssh command itself fails, use the lab's way: Compute Engine > VM instances > SSH, and ping the other office's IP (cat ~/ip1 and cat ~/ip2 print them).

What you just proved: office 1 and office 2 have no direct link. The packets went office 1 > VPN > routing-vpc > VPN > office 2, and the hub is what told each side the other's routes.

## Task 4. Delete resources

STOP: only run this after "Create Hub and Spokes" is green.

```bash
gcloud network-connectivity spokes delete office-1-spoke --region=`cat ~/reg1` --quiet
gcloud network-connectivity spokes delete office-2-spoke --region=`cat ~/reg2` --quiet
gcloud network-connectivity hubs delete ncc-hub --quiet
gcloud network-connectivity hubs list
```

You should see "Listed 0 items." Spokes go first: a hub cannot be deleted while spokes are attached.
